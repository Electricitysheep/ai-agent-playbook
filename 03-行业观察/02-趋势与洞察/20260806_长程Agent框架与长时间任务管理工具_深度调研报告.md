# 长程 Agent（Long-Horizon Agent）框架与长时间任务管理工具深度调研报告

> **报告日期**：2026-08-06  
> **研究截止**：2026-08-06  
> **归档位置**：`06_行业观察/03_趋势与洞察/`  
> **研究范围**：OpenHands（OpenDevin 演进线）、SWE-agent、LangGraph（Time-Travel / Checkpoint）、OSWorld / OSWorld 2.0、Agent-S、InfiAgent、Mage（MAGE）及少量直接可比基线。  
> **证据原则**：关键结论优先采用官方仓库、官方文档、源码、官方基准页面和论文原文；“未发现官方证据”不等于“功能绝对不存在”。

## 我能讲出来的版本（5 行）

1. **长任务可靠性不是上下文窗口问题，而是状态机问题**：模型能看到更多 token，不代表它知道哪条轨迹仍然有效、哪里可以回滚、恢复后从哪一步继续。
2. **LangGraph 是最强的通用断点/时间旅行底座**：Checkpointer、Store、Replay、Fork、Durable Execution 都是显式机制，但上下文压缩和任务语义仍需应用层设计。
3. **InfiAgent 是本次对象中最直接面向“无限运行 + 文件持久化 + Resume”的开源运行时**，但生态、独立评测和许可证约束需要谨慎评估。
4. **OpenHands 是最完整的工程型编码 Agent 平台**：SDK 有 Condenser 与 `persistence_dir`，Agent Canvas 提供后端、沙箱、分支、自动化和评测基础设施；但其长程可靠性依赖部署形态、工作区持久化和模型/任务设计。
5. **OSWorld / Agent-S 更像 GUI 长程评测与执行范式，不是通用断点框架**；MAGE 是值得吸收的执行状态树研究设计，尚不应当当作可直接部署的成熟工具。

## 1. 研究口径：什么才算“长程 Agent”

### 1.1 五个必须拆开的能力

| 能力 | 本报告的判定问题 | 常见误判 |
|---|---|---|
| 抗衰减 | 执行数十到数百步后，任务目标、约束、已完成项和失败原因是否仍可重建？ | 把 1M 上下文窗口当成抗衰减 |
| Context 截断/压缩 | 是否有明确的历史裁剪、摘要、压缩边界、保留策略和错误隔离？ | 把“自动截断”当成“语义正确压缩” |
| Resume / Checkpoint | 进程、网络或工具调用中断后，能否从可识别边界继续，而不是重跑或重新解释？ | 把导出的轨迹文件当成可恢复检查点 |
| 状态持久化 | 状态存在哪：内存、事件日志、数据库、工作区文件、外部 Store？重启后是否仍存在？ | 把会话历史持久化等同于环境状态持久化 |
| 评测闭环 | 是否有可重复环境、轨迹、成功判定、失败分析、回归比较和成本/延迟指标？ | 只报告一次成功率，不报告任务集合和评测协议 |

### 1.2 统一证据标记

- **原生**：官方 API/源码/文档直接提供该机制。
- **可组合**：框架提供底座，但压缩、语义恢复或任务级逻辑需自行实现。
- **有限**：只覆盖轨迹、知识库或结果文件，不构成完整 Resume。
- **未发现**：在本次检查的官方仓库/文档/论文中没有找到直接证据。
- **研究性**：论文明确提出方法，但未验证其为可直接部署的通用工具。

## 2. 结论先行：顶尖工具推荐

### 2.1 按使用目标推荐

| 使用目标 | 首选 | 为什么 | 需要补齐的部分 |
|---|---|---|---|
| **生产级长时间编排底座** | **LangGraph + 持久化 Checkpointer + LangSmith** | 显式线程状态、持久化检查点、Replay/Fork、Human-in-the-loop、可观测与评测生态完整 | 任务规划、上下文压缩、幂等工具、业务状态一致性 |
| **开箱即用的代码 Agent 平台** | **OpenHands Agent Canvas / Software Agent SDK** | 编码工具链、沙箱/远程工作区、Condenser、事件持久化、会话分支、自动化与 SWE-bench 评测链较完整 | 生产环境要配置持久化 backend、工作区快照、权限与成本控制 |
| **真正强调“无限运行 / Resume”** | **InfiAgent MLA V3** | 官方运行时明确提供可恢复执行栈、文件目录记忆、原子写入、工具调用幂等重放、跨进程恢复 | GPL-3.0、生态较小、独立长程基准不足、部分能力来自项目自述 |
| **代码修复研究与 SWE-bench** | **SWE-agent；新项目优先 mini-SWE-agent** | 研究可改造、历史处理器可配置、Docker 执行、批量评测与轨迹浏览成熟 | SWE-agent 已 maintenance-only；没有证据表明它是通用跨日 Resume 运行时 |
| **GUI 长程评测** | **OSWorld 2.0** | 108 个长程任务、平均约 318 次工具调用、任务中位人工时长约 1.6 小时，直接暴露状态跟踪和验证缺陷 | 是 benchmark/environment，不是通用 Agent Runtime；恢复、记忆、压缩需由被测 Agent 提供 |
| **GUI Agent 执行与研究** | **Agent-S3** | OSWorld/WAA/AndroidWorld 结果突出，规划器、Worker、经验记忆和多平台 ACI 完整 | 当前主线更偏单次 rollout 与经验增强，不是显式跨进程任务 checkpoint 系统 |
| **执行状态记忆研究** | **MAGE（论文）** | 用层级状态树、Grow/Compress/Maintain/Revise 解决路径完整性、压缩和错误隔离 | 研究原型定位；本次未发现可直接部署的官方通用 runtime/repository |

### 2.2 最稳妥的组合方案

如果目标是搭建自己的长程 Agent，而不是单纯比较论文：

```text
LangGraph Checkpointer / Store
        +
任务级幂等状态（数据库或文件）
        +
OpenHands / SWE-ReX / 自定义工具执行沙箱
        +
OpenHands Condenser 或 InfiAgent 式分段摘要
        +
LangSmith / OpenHands eval / OSWorld 2.0 / SWE-bench
```

核心决策：**用 LangGraph 管“可恢复的控制流”，用工作区/数据库管“真实任务状态”，用 Condenser/MAGE 思路管“模型可见上下文”**。不要把三者混成一个聊天历史数组。

## 3. 按长程任务生命周期比较

### 3.1 规划：把目标拆成可恢复边界

- **OpenHands**：SDK 提供 Task Tracker Tool；Agent Canvas 的 `/goal` 机制可使用 judge LLM 反复检查目标是否完成。适合工程任务，但目标循环不是通用状态图语义。
- **SWE-agent**：以 GitHub issue 为问题入口，单 Agent + 工具交互为主；可配置 YAML 和历史处理器，适合研究不同 Agent scaffold，不是面向跨日业务流程的计划编排器。
- **LangGraph**：将规划显式编码为节点/边，确定性步骤与 LLM 步骤可混合；最适合把“阶段边界”编码成可持久化状态。
- **Agent-S**：S1 的 Manager 先生成高层计划，再转换为 DAG 并拓扑排序；失败时带 `failure_feedback` 重新规划。它是 GUI 执行内的层级规划，不是跨进程工作流引擎。
- **InfiAgent**：通过 YAML 定义多级 Agent 层级，Researcher/OpenCowork 这类配置将任务拆给不同层级的子 Agent。
- **MAGE**：把 subgoal boundary 作为压缩、维护和回滚的关键边界；规划与记忆管理耦合得最紧。

**判断**：长任务最需要的是“可验证的阶段边界”，而非一段很长的自然语言计划。LangGraph 的节点边界和 MAGE 的 subgoal boundary 是最可迁移的两个设计。

### 3.2 执行：工具调用必须可重放、可观测、可隔离

- **OpenHands**：SDK 使用 Agent/Tool/Workspace/Event 模型；LocalWorkspace、DockerWorkspace、RemoteAPIWorkspace 可切换。Agent Canvas 后端可部署在本机、Docker、VM、Modal 或 Cloud，适合持续运行。
- **SWE-agent**：Docker sandbox、SWE-ReX 和独立 subprocess 模式降低环境状态污染；mini-SWE-agent 明确用每次独立 `subprocess.run`，避免长期 shell session 被破坏，但也牺牲会话级 shell 状态。
- **LangGraph**：Durable Execution 要求把副作用包在任务/节点中，并处理幂等性；它不会自动让外部 API、文件写入或数据库操作变得可重放。
- **OSWorld**：提供可控制的真实桌面环境、初始化状态、跨应用任务和执行后评估；重点是统一实验环境，不是 Agent 工具调用实现。
- **Agent-S**：ACI 负责 GUI ground/action，Manager/Worker 分离计划与执行；支持 Linux、macOS、Windows，但 Python 控制桌面具有高权限风险。
- **InfiAgent**：`ToolExecutor`、事件发射器和后台任务状态结合；官方 RUNTIME.md 声称中断工具调用可在 Resume 时幂等重放。
- **MAGE**：把 action-observation trace 作为底层树节点，错误路径作为分支保留但不进入当前有效路径。

**判断**：工具执行的“幂等重放”是 Resume 成败的底线。没有幂等语义的 checkpoint 只恢复了 prompt，可能重复付款、重复提交或重复写文件。

### 3.3 Context 截断与抗衰减

| 工具 | 机制 | 抗衰减评价 |
|---|---|---|
| OpenHands SDK | `LLMSummarizingCondenser` 在历史超过阈值时总结旧事件，可保留前若干事件；示例同时使用 `persistence_dir` 重载会话 | **强**：有显式压缩器和持久化，但摘要质量仍受模型影响；需保留任务状态与关键工具结果 |
| SWE-agent | `LastNObservations` 只保留最近 N 个 observation；`ClosedWindowHistoryProcessor` 关闭过期文件窗口；可打 tag 强制保留 | **中**：机制清晰、可配置，但多数是裁剪/省略，不是任务级状态重建 |
| LangGraph | 核心是状态持久化与编排，官方定位为 low-level orchestration；没有规定统一的上下文压缩器 | **可组合**：自由度最大，默认抗衰减能力取决于应用实现 |
| OSWorld | 基准分析显示长文本轨迹历史通常比仅截图历史更有利，但效率与上下文成本上升 | **评测暴露问题**：它测量衰减，不解决衰减 |
| Agent-S | 规划器保留 planner history；KnowledgeBase 以 episodic/narrative memory JSON + embeddings 做相似经验检索；任务内有子任务完成/失败反馈 | **中**：经验增强有助于跨任务，但相似检索不等于当前执行状态恢复，且实时轨迹上下文仍有限 |
| InfiAgent | short action windows、thinking summaries、file relay；同时维护压缩后的 `action_history` 与完整 `action_history_fact`；ContextBuilder 按 token/context 设置选择历史 | **强**：把“遗忘”设计成运行时机制，但摘要/文件状态的一致性需要应用验证 |
| MAGE | 两层状态树；Compress 只在完成 subgoal 或超过阈值时压缩；Maintain 验证摘要；Revise 回滚并分支 | **研究上最完整**：同时处理压缩、状态路径和错误隔离，但尚非成熟生产组件 |

**关键结论**：

1. “截断”有三种不同含义：删除旧 observation、摘要旧事件、从外部状态重建当前执行状态。三者可靠性依次提高，但实现复杂度也提高。
2. InfiAgent 的“完整轨迹留存 + 模型可见历史压缩”与 OpenHands 的 Condenser 是工程上最可用的两种路线。
3. MAGE 提醒我们：压缩必须绑定 subgoal boundary，并保留可回滚边界；否则摘要一旦错，错误会污染后续所有步骤。

### 3.4 Resume / Checkpoint / Time-Travel

| 工具 | 断点能力 | 实际语义 |
|---|---|---|
| LangGraph | **原生强** | Checkpointer 保存 thread graph state；Replay 从旧 checkpoint 继续；Fork 以旧 checkpoint 建新分支；原历史保留。注意 Replay 会重新执行 checkpoint 之后的节点，LLM/API/interrupt 可能产生不同结果。 |
| OpenHands SDK | **原生中强** | Conversation 可用 `persistence_dir` 持久化事件；SDK 有事件回放与 `ConversationState.get_unmatched_actions` 恢复基准；Agent Canvas 支持会话分支。恢复粒度更多是事件/会话，不等于所有外部副作用自动回滚。 |
| OpenHands Agent Canvas | **平台级强** | 后端可运行在 always-on VM/Cloud；本地进程停止后需重启，Docker/VM/Cloud 后端可持续；分支保留会话、配置、工作区上下文和 backend state。 |
| InfiAgent | **原生强（项目自述 + 源码线索）** | `user_root/tasks`、conversation 和 execution stack 持久化；原子写入、损坏隔离、工具调用幂等重放；Web UI/CLI 提供 Resume。需要在真实部署中验证跨机器和外部副作用边界。 |
| SWE-agent | **有限** | 官方文档强调批量结果写入 `preds.json`，中断时可能出现缺失，可用 `merge-preds` 修复结果文件；本次未发现官方通用 checkpoint/resume 机制。 |
| Agent-S | **未发现完整原生 Resume** | `reset()` 初始化 planner/worker 与计数器；KnowledgeBase 可跨运行保存经验，但这不是将当前 UI 会话从任意步骤恢复。 |
| OSWorld | **环境级有限** | 支持 intermediate initial state、轨迹写入和结果目录；主要用于从固定初始状态重跑评测，不是恢复任意 Agent 进程。 |
| MAGE | **研究性强** | Revise 明确定义为从历史边界恢复并在新分支继续；论文级方法，不等于现成 API/服务。 |

**最重要的区别**：

- **Resume**：继续原任务；
- **Replay**：从某 checkpoint 重执行后续节点；
- **Fork / Time-Travel**：保留原路径，创建替代路径；
- **Restore**：恢复 Agent 内部状态；
- **Rollback**：还要处理外部环境副作用。

只有 LangGraph 和 MAGE 明确把“从历史边界分支”作为一等概念；OpenHands 和 InfiAgent 更偏向事件/栈恢复；SWE-agent、Agent-S、OSWorld 主要保存轨迹或经验。

### 3.5 状态持久化

#### OpenHands

OpenHands SDK 的 Conversation 示例使用 `persistence_dir="./.conversations"`，删除内存对象后重新实例化仍可继续发送消息。SDK 事件回放基准以 `events/event-<seq>-<uuid>.json` 形式测量索引重建、完整回放和 `get_unmatched_actions` 恢复耗时。Agent Canvas 则将会话、设置、MCP、自动化和工作区关系置于选定 backend；切换 backend 就切换运行环境和状态边界。

**优点**：事件源模型、会话分支、沙箱/远程工作区、工程生态完整。  
**风险**：事件恢复不自动撤销已经发生的外部 API 副作用；本机安装关闭进程就停，需要 always-on backend 才能持续工作。

#### SWE-agent

主要持久化产物是轨迹、预测/补丁和批量结果，适合研究复盘和 benchmark 对比。官方文档明确指出中断批量运行时 `preds.json` 可能不完整，`merge-preds` 只修复结果汇总，不是从任意工具调用边界恢复 Agent 内部状态。

#### LangGraph

官方将 Checkpointer 与 Store 明确分工：

- Checkpointer：单 thread 的 graph state snapshot，服务于对话连续性、Human-in-the-loop、Time Travel、容错。
- Store：跨 thread 的应用级 key-value 数据，服务于偏好、事实、共享知识。
- InMemorySaver/MemoryStore 重启即丢；生产需使用 SQLite/Postgres 等持久化实现。
- 长对话 checkpoint 会无限增长，需要裁剪或 retention policy。

这是本报告中最清晰的“短期执行状态 / 长期跨任务记忆”分层。

#### OSWorld / Agent-S

OSWorld 保存环境初始配置、任务 evaluator、轨迹和结果；Agent-S 将 episodic/narrative memory 和 embeddings 存在工作区 KB。二者都能保存“可复盘信息”，但没有直接证据证明能恢复完整的 Agent + 环境 + 外部副作用三元状态。

#### InfiAgent

官方运行时说明给出最完整的工程化持久化语义：`user_root/tasks/<task_id>/` 保存任务状态，`user_root/conversations/` 保存会话，执行栈/动作状态原子写入；源码中 AgentExecutor 还区分压缩后的渲染历史、完整事实轨迹、execution/thinking trace、待执行工具队列。ContextBuilder 按 task 目录读取历史、经验、技能和最近交互，旧任务可通过 `task_history_search` 查询。

**优点**：状态外置、文件可审计、无外部数据库即可工作。  
**风险**：文件系统状态仍需与真实世界副作用保持一致；跨机器恢复要求共享/同步 `user_root` 和工作区。

#### MAGE

论文将持久状态抽象为可分支的层级执行树，而不是普通向量库。底层节点是 action-observation，顶层节点是 subgoal summary，当前状态是 root-to-current path。论文没有把它包装成长期运行服务或通用数据库产品。

## 4. 各工具工具卡

### 4.1 OpenHands（OpenDevin 演进线）

**定位变化**：历史 OpenDevin 入口已指向 `OpenHands/OpenHands`；截至本报告日期，主仓库 README 的产品重点是 Agent Canvas，而可复用 Agent 核心在 `OpenHands/software-agent-sdk`。

**长程机制**：

- SDK：Agent、Conversation、Tools、Workspace、Events、Condenser、Security。
- Condenser：`LLMSummarizingCondenser` 在历史超过阈值后总结旧事件，保留首部关键事件。
- 持久化：Conversation 使用 `persistence_dir`；事件目录可索引、回放并分析未匹配动作。
- 平台：Agent Canvas 支持本地、Docker、VM、Modal、Cloud backend；会话可从消息点分支。
- 评测：SDK 仓库提供 eval 管理技能，覆盖 SWE-bench、GAIA、SWE-bench Pro、TerminalBench 等，并保存结果报告和成本数据。

**优势**：代码 Agent 工具链和部署边界最完整；比单纯 Agent loop 更接近生产控制面。  
**短板**：Condenser 是摘要，不是事务回滚；工作区、数据库、网络 API 需要应用自己实现幂等和补偿。  
**推荐**：企业代码 Agent、需要 UI + backend + sandbox + automation 的团队。

### 4.2 SWE-agent / mini-SWE-agent

**定位**：SWE-agent 从 GitHub issue 自动修复代码，研究目标是 Agent-Computer Interface；官方文档已明确 SWE-agent maintenance-only，建议新项目使用 mini-SWE-agent。

**长程机制**：

- `history_processors.py` 提供 `LastNObservations`、`ClosedWindowHistoryProcessor`、cache control 与 tag 保留机制。
- Docker/SWE-ReX 负责环境隔离。
- 批量模式支持并行、SWE-bench、轨迹浏览和 `preds.json` 汇总。
- mini 版本采用完全线性的历史和每次独立 subprocess，换取简单、稳定、易评测。

**优势**：研究可复现、历史处理器可组合、SWE-bench 闭环成熟。  
**短板**：历史处理以观察裁剪为主；批量输出可修复但没有通用跨进程 Resume；原项目已进入维护模式。  
**推荐**：SWE-bench/代码修复实验、研究 Agent scaffold、希望快速验证 tool protocol 的团队；生产长程编排不要单独依赖它。

### 4.3 LangGraph：Checkpointer + Time-Travel

**定位**：低层 Agent orchestration runtime，不规定 prompt 或 Agent 架构；官方核心卖点是 durable execution、persistence、streaming、human-in-the-loop、memory 和可观测/评测集成。

**长程机制**：

- Checkpointer 按 `thread_id` 保存 graph state snapshots。
- Store 保存跨 thread 的应用级长期数据。
- Replay：从旧 checkpoint 继续，之前节点不重跑，之后节点重跑。
- Fork：从旧 checkpoint 更新状态创建新分支，原历史保留。
- Interrupt：暂停后用 `Command(resume=...)` 继续。
- Durable Execution：副作用必须被设计为幂等，节点要可安全重试。
- 官方文档提醒 checkpoint 会增长，需要 retention/pruning。

**优势**：断点、回放、分支、人工介入和状态作用域都是显式 API；最适合作为长期任务的控制平面。  
**短板**：核心不替你做上下文压缩、语义摘要、文件版本快照、外部副作用补偿或最终评测；这些属于应用层/生态层。  
**推荐**：复杂审批流、研究流程、跨日任务、需要人工介入与审计的生产 Agent。

来源：

- [LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)
- [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- [Use time-travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)
- [LangGraph GitHub](https://github.com/langchain-ai/langgraph)

### 4.4 OSWorld / OSWorld 2.0

**定位**：真实计算机环境与 Agent benchmark，不是通用 Agent Runtime。

**OSWorld 1.0**：369 个跨应用真实电脑任务，提供初始状态设置、环境控制、执行后 evaluator、并行运行、轨迹和结果；原始基准页面报告人类成功率超过 72%，早期最佳模型仅 12.24%。

**OSWorld 2.0**：2026-06 发布，明确以长程真实工作流为目标：

- 108 个任务；
- 69.6% 任务需要超过 1 小时的人类操作时间；
- Claude Opus 4.7 约 318 次工具调用，平均超过 250 steps 的任务统计；
- 27.25 个平均 scoring checkpoints；
- 500-step binary completion 下，官方页面报告 Claude Opus 4.8 最佳也仅 20.6% binary reward、54.8% partial score；
- 随任务时长增加，成功率快速下降，超过 163 分钟的保留任务在图表中没有模型完成。

**它对长程 Agent 的价值**：它把“状态跟踪、跨源推理、动态环境、隐式状态、冲突消解、最终验证”变成可重复任务和 evaluator，尤其适合验证抗衰减，而非仅测 GUI 单步准确率。

**局限**：任务状态、VM、资产、网站、评测器有严格版本锁定；benchmark 自身不提供 Agent checkpoint。若 Agent 中途掉线，通常需要使用自己的持久状态或重新从固定初始状态运行。

### 4.5 Agent-S

**定位**：Simular AI 的开源 GUI Agent；通过 Agent-Computer Interface 使用电脑，支持 Linux、macOS、Windows，当前仓库主线包含 S1/S2/S2.5/S3。

**长程机制**：

- S1 `GraphSearchAgent` 将 Manager 规划器与 Worker 执行器分开。
- Manager 先生成 high-level plan，再翻译为 DAG 并拓扑排序。
- 失败时记录 `failure_feedback`，重新规划并重置 executor state。
- KnowledgeBase 保存 `episodic_memory.json`、`narrative_memory.json` 和 embeddings；相似任务经验在首次规划时检索。
- `reset()` 会重建 planner/worker、计数器和当前 subtask；这说明默认任务运行是 rollout 状态机，不是跨进程 checkpoint。
- 官方 README 报告 Agent S3 在 OSWorld 100-step 设置下单 Agent 66%，加入 Behavior Best-of-N 后 72.6%；WindowsAgentArena 56.6%、AndroidWorld 71.6%。这些是 benchmark 结果，不是 Resume 保证。

**优势**：GUI 规划、经验增强、跨平台 ACI 和公开 benchmark 结果突出。  
**短板**：相似经验检索不能替代当前执行状态树；本次未发现完整的任务栈持久化/工具幂等重放/跨进程 Resume API。  
**推荐**：GUI Agent 研究、OSWorld/WAA/AndroidWorld 实验；若要长时间生产任务，应外接 LangGraph/InfiAgent 式状态层。

### 4.6 InfiAgent（MLA V3）

**定位**：配置驱动、多级 Agent、强调 unlimited runtime 的开源运行时。必须区分当前 `polyuiislab/infiAgent`（MLA V3，面向无限运行）与早期 `InfiAgent/InfiAgent`（InfiAgent-DABench / DA-Agent，数据分析 Agent 框架与评测）。

**长程机制**：

- 配置定义 Agent 层级，而非每个 Agent 都写成类。
- short action windows + thinking summaries + file relay 构成 forgetting loop。
- `user_root/tasks/<task_id>/`、`user_root/conversations/` 外置任务和会话状态。
- 2026-07 更新说明原子写入（temp + fsync + rename）、损坏状态隔离、工具调用幂等重放、跨进程 file lock、乐观并发版本和 transactional task/global writes。
- `AgentExecutor` 区分压缩渲染历史、完整事实轨迹、execution/thinking traces、pending tools。
- `ContextBuilder` 基于 token budget、最近历史、经验 store、技能和任务目录重建上下文；历史不足时用 `task_history_search` 检索旧任务。
- CLI/Web UI 均提供 Resume；项目 README 还说明了跨进程/跨机器恢复的目标。

**优势**：在“长时间运行、崩溃恢复、文件化记忆、成本/上下文控制”上最直接。  
**短板**：GPL-3.0 对闭源商业集成有约束；长程能力主要由项目官方说明和源码体现，尚缺与 OSWorld 2.0 / MemoryArena 同协议的独立结果；文件状态与外部副作用一致性仍需业务层验证。  
**推荐**：个人/研究者长时间写作、资料整理、代码/文档自动化；接受 GPL 且愿意自己管理 workspace 的团队。

### 4.7 Mage / MAGE：执行状态树研究范式

**名称澄清**：本报告中的 Mage 指论文 *Beyond Semantic Organization: Memory as Execution State Management for Long-Horizon Agents*，即 **Memory as Agent-Guided Exploration**。它不同于 Mage.ai 数据管道，也不同于其他同名 MAGE 元强化学习/安全研究项目。

**核心设计**：

- 两层层级状态树：底层 action-observation trace；顶层 subgoal summary。
- 当前状态取 root-to-current path，而非从相似记忆池拼接。
- **Grow**：追加轨迹；**Compress**：在 subgoal boundary 或阈值处压缩；**Maintain**：验证摘要和底层轨迹；**Revise**：回到目标边界，新分支继续，错误段不进入 active path。
- 节点含 `id`、`content`、`parent`、`children`、顶层摘要的 `cover_nodes` 和诊断 `note`。
- MemoryArena 实验报告平均成功率较 baseline 提升 7.8–20.4 个百分点，较 long-context approach 节省 55.1% token。

**优势**：把上下文压缩、错误定位、回滚、分支和状态完整性放进一个闭环；这是本次研究中对“抗衰减”解释力最强的模型。  
**短板**：论文是方法贡献，不等同于生产 SDK；本次未在论文页面找到可直接部署的官方通用 GitHub runtime。  
**推荐**：作为自研 Agent 的 memory/checkpoint 设计参考，而非直接选型为现成平台。

来源：

- [MAGE arXiv 摘要](https://arxiv.org/abs/2606.06090)
- [MAGE HTML 全文](https://arxiv.org/html/2606.06090)

## 5. 多维比较矩阵

等级含义：`5 = 原生且明确`，`4 = 原生但有边界`，`3 = 可组合/部分覆盖`，`2 = 有轨迹或经验但不是完整机制`，`1 = 未发现或不属于该工具定位`。这不是统一 benchmark 分数，而是基于官方能力证据的选型等级。

| 工具 | 抗衰减 | Context 压缩 | Resume / Checkpoint | 状态持久化 | Time-Travel / Fork | 评测闭环 | 沙箱/环境 | 长程定位 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **LangGraph** | 4 | 3 | **5** | **5** | **5** | 4（配 LangSmith） | 3 | 通用控制平面 |
| **OpenHands SDK / Canvas** | 4 | **4** | 4 | **4** | 4（会话分支） | **5** | **5** | 工程型代码 Agent 平台 |
| **InfiAgent MLA V3** | **5** | **4** | **5** | **5** | 3（Resume 强，显式 Fork 弱） | 3 | 4 | 无限运行 Agent runtime |
| **SWE-agent** | 3 | 4 | 2 | 3 | 1 | **5（SWE-bench）** | 4 | 代码修复研究 |
| **mini-SWE-agent** | 3 | 2（线性历史） | 2 | 2 | 1 | **5** | 4 | 极简代码修复 |
| **OSWorld 2.0** | 5（测量） | 1（不提供） | 2（固定初始状态） | 3（轨迹/结果） | 1 | **5** | **5** | GUI 长程 benchmark |
| **Agent-S3** | 4 | 3 | 2 | 3（KB） | 1 | **5（OSWorld/WAA/AW）** | 4 | GUI Agent |
| **MAGE** | **5（研究设计）** | **5（边界压缩）** | **5（论文语义）** | 4（树持久化抽象） | **5** | 4（MemoryArena） | 1 | 执行状态记忆范式 |

### 5.1 为什么不做简单总分排名

简单加权会掩盖定位差异：OSWorld 2.0 的评测闭环可以是 5，但它不是 runtime；LangGraph 的 Resume 可以是 5，但它不会自动给你一个可靠的 Agent；Agent-S 的 benchmark 结果可以很高，但不能推出它支持跨进程恢复。因此本报告使用“按目标推荐”，而不是把 benchmark、框架能力和论文方法混成一个总分。

## 6. 五类工具在长程任务上的优劣总结

### 6.1 抗衰减

**最强思想**：MAGE 的 active root-to-current path + subgoal boundary + Revise。  
**最强工程实现**：InfiAgent 的 forgetting loop + 外置任务状态；OpenHands Condenser 的 event summarization。  
**最强评测暴露**：OSWorld 2.0，直接把长任务成功率按时长、工具调用、跨源状态和最终验证拆开。  
**常见失败**：Agent-S 的经验检索、SWE-agent 的 Last-N observation 都可能让模型看到“相关内容”，但未必重建“当前有效状态”。

### 6.2 Context 截断

- **删除观察**：SWE-agent；成本低、可控，但可能删除关键中间状态。
- **摘要事件**：OpenHands；保留历史骨架，摘要质量是风险点。
- **窗口 + 文件外置**：InfiAgent；把事实轨迹和可见轨迹拆开，适合无限运行。
- **状态树压缩**：MAGE；压缩只发生在完成边界，且摘要可被验证和回滚。
- **应用层自定义**：LangGraph；自由度最大，责任也完全在开发者。

### 6.3 断点恢复

推荐把 checkpoint 设计成四层：

1. **控制流 checkpoint**：当前节点、下一节点、重试次数、分支 id。
2. **模型上下文 checkpoint**：摘要、最近 trace、关键约束、失败诊断。
3. **环境 checkpoint**：工作区 commit、容器/VM snapshot、数据库事务状态。
4. **副作用 ledger**：外部 API、邮件、支付、提交等是否已完成及幂等 key。

LangGraph 解决第 1 层最好；OpenHands/InfiAgent 对第 2–3 层更接近现成实现；第 4 层没有任何框架能替业务自动解决。

### 6.4 状态持久化

- **内存 saver** 适合 demo，不适合长任务。
- **文件状态** 审计方便、部署简单，但必须做原子写入、锁和版本校验。
- **事件溯源** 适合回放与审计，但历史会增长，需索引、压缩和保留策略。
- **数据库 checkpointer/store** 适合多实例和生产，但 schema、迁移、锁和成本更重。

### 6.5 评测闭环

强闭环至少要有：

```text
固定环境/任务版本
  → 轨迹与工具调用记录
  → 可执行 evaluator
  → binary + partial reward
  → 失败归因
  → 成本/时延/步骤统计
  → 同任务回归比较
```

OSWorld 2.0 在 GUI 长程上最完整；SWE-agent 在代码修复批量评测上最成熟；OpenHands 已把 SWE-bench/GAIA 等 eval 管理纳入工程流程；LangGraph 需要配 LangSmith 或自建 evaluator；InfiAgent 需要补统一、公开、可比较的长程 benchmark。

## 7. 面向实际落地的选型决策树

### 7.1 我需要“跑几小时/几天的代码或资料工作”

- 需要开箱即用、沙箱、GUI、自动化：**OpenHands Agent Canvas**。
- 需要明确 Resume、文件化记忆、跨会话持续：**InfiAgent**。
- 需要自定义状态机、审批、人工介入：**LangGraph + OpenHands/SWE 工具层**。

### 7.2 我需要“自动修复大量 GitHub issue”

- 研究与 benchmark：**SWE-agent**。
- 新项目、极简、快速评测：**mini-SWE-agent**。
- 要加 durable workflow、人工审核、跨系统状态：在外层加入 **LangGraph** 或 OpenHands Agent Server。

### 7.3 我需要“让 Agent 操作桌面 GUI”

- 评测基准：**OSWorld 2.0**。
- Agent 算法与跨平台执行：**Agent-S3**。
- 生产级长程任务：Agent-S/OSWorld 只负责 GUI 环境与执行器，另加 checkpoint、workspace snapshot、事件日志和业务 ledger。

### 7.4 我需要“研究长程记忆算法”

- 直接理解执行状态管理：**MAGE**。
- 可运行工程基线：**LangGraph** 或 **InfiAgent**。
- 对照组：全历史、Last-N observation、RAG/embedding memory、OpenHands Condenser。
- 评测：MemoryArena + OSWorld 2.0 + 自建跨 session 任务，不要只测事实召回。

## 8. 推荐的最小生产架构

```text
┌──────────────────────────────────────────────────────────┐
│ Task API / Human UI / Scheduler                          │
└──────────────────────┬───────────────────────────────────┘
                       │ task_id, goal, policy
┌──────────────────────▼───────────────────────────────────┐
│ LangGraph durable control flow                           │
│ - current_node / retry / branch / interrupt             │
│ - PostgresSaver or durable checkpointer                 │
└───────────────┬──────────────────────┬──────────────────┘
                │                      │
┌───────────────▼──────────────┐ ┌─────▼───────────────────┐
│ Context/state manager         │ │ Environment + tools      │
│ - subgoal summaries           │ │ - OpenHands/SWE tools    │
│ - recent raw trace            │ │ - Docker/VM workspace    │
│ - active constraints          │ │ - idempotency keys       │
│ - failed branch diagnostics   │ │ - workspace snapshots    │
└───────────────┬──────────────┘ └─────┬───────────────────┘
                │                      │
                └──────────────┬───────┘
                               │
┌──────────────────────────────▼───────────────────────────┐
│ Evaluation / Observability                               │
│ LangSmith traces + task evaluator + cost/latency + diff │
└──────────────────────────────────────────────────────────┘
```

### 8.1 必须实现的状态字段

```text
task_id
run_id / branch_id
current_node / next_node
subgoal_id / completed_subgoals
active_constraints
recent_trace
compressed_state
failure_feedback
workspace_revision
pending_tool_calls
completed_side_effects
retry_count / budget / deadline
```

### 8.2 必须验证的恢复场景

1. LLM 请求超时后恢复，不重复执行已成功工具。
2. 工具进程在写文件中途崩溃，恢复后能检测半写入并重试/隔离。
3. 人工 interrupt 后改变状态，再从原 checkpoint Fork。
4. 工作区 commit 与 checkpoint 不匹配时拒绝盲目继续。
5. 历史摘要错误时能够回到 subgoal boundary，而不是继续污染当前路径。
6. 外部 API 已成功但响应丢失时，使用幂等 key 查询结果，而不是重复调用。

## 9. 证据边界与未决问题

- **OpenHands**：官方事件回放与 Condenser 证据充分；“所有外部副作用可回滚”没有证据，不能这样宣传。
- **SWE-agent**：历史处理器和评测链证据充分；通用 Resume 本次未发现，不能把 `preds.json` 当 checkpoint。
- **LangGraph**：Time-Travel/Checkpoint 证据最明确；上下文压缩、外部事务和环境 snapshot 不是核心内置能力。
- **OSWorld 2.0**：长程评测事实强，但不能据此说任何 Agent 自动支持恢复。
- **Agent-S**：公开 benchmark 和规划/经验代码强；跨进程任务状态恢复证据不足。
- **InfiAgent**：运行时源码与 README 对无限运行、原子持久化、Resume 描述非常直接；仍需独立第三方 benchmark 验证真实长任务成功率和跨机器恢复。
- **MAGE**：论文提供清晰机制和 MemoryArena 结果；本次未发现官方生产级通用代码仓库，因此只作为架构范式，不作为直接采购/部署选项。
- **OSWorld 2.0 版本注意**：官方仓库要求使用 pinned release（当前页面列出的 `osworld-v2-2026.06.24`）及配套任务、资产和网站版本，不能把 `main/latest` 混入可比评测。

## 10. 最终建议

### 推荐排序（按“长程任务管理”而非单次 benchmark）

1. **LangGraph**：最强的通用 durable control-flow / checkpoint / time-travel 底座。
2. **OpenHands SDK / Agent Canvas**：最完整的代码 Agent 工程平台，适合直接落地。
3. **InfiAgent MLA V3**：最直接的无限运行与文件化 Resume 方案，适合个人和研究部署；使用前审查 GPL 与生态风险。
4. **OSWorld 2.0**：最值得采用的 GUI 长程评测闭环，不是 Agent runtime。
5. **Agent-S3**：GUI Agent 研究与执行强，但需外接 durable state 才适合长任务。
6. **SWE-agent / mini-SWE-agent**：代码修复 benchmark 强，通用长任务恢复能力有限。
7. **MAGE**：最值得吸收的记忆/状态管理设计，不是现成生产工具。

### 一句话决策

> **要买/搭系统：LangGraph 管 checkpoint，OpenHands 管代码工具与沙箱，InfiAgent 的文件化持久化和 MAGE 的状态树管抗衰减，OSWorld 2.0 管长程评测；不要把任何单一组件误当成完整的 Long-Horizon Agent。**
