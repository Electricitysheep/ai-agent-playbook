## 第 0 章　先看这张地图

工具很多，但按「谁在用、解决什么」切开只有六格。先记住这张表，后面每一章都是在填格子。

| | 数据分析岗 | 投研岗 | 企业财务岗 |
|---|---|---|---|
| **取数** | SQL / BigQuery / Snowflake | Wind / Choice / Bloomberg / EDGAR API | ERP 总账 / 子账导出 |
| **加工** | dbt / Python / Spark | Excel 模型 / Python 因子库 | Excel / BlackLine / Trintech |
| **呈现** | Tableau / Power BI / Looker | Excel + PPT 研报 | 合并报表 / 管报 / 董事会材料 |

**一句话概括三个岗位的差别**：数据分析岗的数据是**自家产生的**，投研岗的数据是**外面拿来的**，企业财务岗的数据是**必须对外负责的**。这决定了三者对工具的要求完全不同——数据分析岗要快，投研岗要全，企业财务岗要准且可审计。

## 第 1 章　数据分析工具栈：大厂日常用什么

### 1.1 五层结构

2026 年的数据分析工具按五类划分：**查询与提取、脚本与统计、可视化与 BI、现代数据栈基础设施、AI 辅助分析**。

| 层 | 主流工具 | 你必须会的 | 说明 |
|---|---|---|---|
| **查询提取** | SQL、BigQuery、Snowflake | **SQL（不可替代）** | 一切的地基。AI 能帮你写，但你必须能读懂并判断对错 |
| **脚本统计** | Python、R | **Python** | pandas / polars / numpy；R 在互联网大厂已边缘化 |
| **可视化 BI** | Tableau、Power BI、Looker | 至少一个 | 见下面的选型规则 |
| **现代数据栈** | dbt、Snowflake、Spark | **dbt** | 分析工程师的核心工具，2026 年的硬通货 |
| **AI 辅助** | Code Interpreter、Copilot、Hex Magic | 会用 + 会验证 | 第 5–7 章展开 |

**科技公司/创业公司的数据分析师必会清单**：SQL、Python、dbt、Looker 或 Tableau；次要工具是 Snowflake/BigQuery 和 Git。

### 1.2 BI 选型的三条决策规则

不用纠结哪个"最好"，业界的选型规则很直白：

- **微软生态** → Power BI（Office 365 已经买了，边际成本最低）
- **视觉分析文化** → Tableau（探索式分析体验最好）
- **需要治理型语义层** → Looker（指标定义集中管理，防口径分叉）

如果团队用 dbt，2026 年配合最好的 BI 是 **Omni、Lightdash、Looker、Hex、Mode**——按优先级选：要 dbt 双向集成 + 原生 AI 选 Omni，要开源选 Lightdash，要 notebook 风格（SQL 和 Python 挨着 dbt 模型写）选 **Hex**。

### 1.3 Notebook 这一层值得单独说

**Hex** 是把 SQL、Python、无代码和 AI cell 混在一起的协作工作区，带 Notebook Agent（从提示词起草查询和应用），并与 dbt Cloud 及 dbt 语义层集成。分析师做探索性工作时，**Hex 或 Mode** 是主流选择。

对个人学习者的含义：Jupyter 够用，但要知道工业界已经把 notebook 做成了协作产品——**面试时能说出 Hex/Mode 与 Jupyter 的差别（版本管理、权限、可发布为应用、连语义层），是个加分信号**。

### 1.4 一个务实的建议

工具清单看起来吓人，但**真正每天用的就三个：SQL、Python、一个 BI**。其余的是"知道存在、需要时能查"。不要陷入工具收集癖——第 9 章的路径里，我把优先级排死了。

## 第 2 章　财务分析工具栈（上）：投研端

### 2.1 四大终端的定位与价格带

| 终端 | 定位 | 关键事实 | 谁在用 |
|---|---|---|---|
| **Wind 万得** | 中国金融业事实标准 | 券商/基金/银行/保险/私募**市占率 90%+**；20+ 年历史；价格**数万到数十万元/年**；学习曲线陡 | 国内机构，几乎人手一个 |
| **Choice 东方财富** | 高性价比替代 | 用户反馈**约 10% 的价格实现 95%+ 的功能**；体验更友好 | 个人专业投资者、高校、中小券商 |
| **Capital IQ（S&P）** | 全球公司库 | 覆盖上市 + 非上市 + PE；财务数据、股价、盈利预测；**筛选工具与 Excel 插件方便** | 投行、PE、跨境研究 |
| **FactSet** | 投行标配 | 面向投资专业人士的分析应用；**Excel 插件强** | 投行、买方研究 |
| **Bloomberg** | 全球市场与固收 | 终端 + 消息 + 交易；固收与外汇优势明显 | 全球宏观、交易台 |

**给求职者的现实提示**：这些都是机构付费产品，个人几乎不可能拿到。**但这不是障碍**——面试官关心的不是你有没有 Wind 账号，而是**你知不知道它解决什么问题、以及没有它你怎么办**。第 9 章的练习项目全部用公开数据完成，逻辑与用 Wind 完全一致。

### 2.2 免费与低成本替代路径

| 需求 | 机构方案 | 你能用的 |
|---|---|---|
| 美股财报结构化数据 | Capital IQ / FactSet | **SEC EDGAR XBRL API**（免费、覆盖 8,000+ 家、标准 US-GAAP 字段名）+ `edgartools` / `sec-api` |
| A 股财报原文 | Wind | **巨潮资讯网**（法定披露平台）+ 交易所官网 |
| A 股结构化数据 | Wind / Choice | AKShare、Tushare（部分免费）、东方财富网页接口 |
| **管理层口径拆解** | Wind 会议纪要 | **《投资者关系活动记录表》**——公司官网 IR / 巨潮 / 中财网，**完全免费，且价值极高** |
| 估值分位 | Wind | 理杏仁、亿牛网（部分免费） |

> **重点标记**：《投资者关系活动记录表》这一项，是我在实际做个股分析时发现的最大信息差。管理层在问答环节给出的口径拆解——比如毛利率提升里一次性因素占多少、汇兑影响的具体金额——**媒体转述几乎必然漏掉，而它往往直接改写结论**。免费的东西里，这是含金量最高的。

### 2.3 Excel 插件是投研端的真实工作面

Capital IQ 和 FactSet 的核心竞争力之一是 **Excel 插件**：在单元格里写函数直接拉数，模型自动更新。这意味着投研端的实际工作流是：

```
终端 Excel 插件拉数 → Excel 建模 → 手工检查勾稽 → 出 PPT/Word 研报
```

**这条链的痛点非常清楚**：Excel 模型没有版本管理、没有自动测试、口径散落在单元格里、换个人接手就崩。第 9 章的练习项目本质上就是**用工程手段重做这条链**——这正是"AI 时代的投研工具人"与"传统投研工具人"的分水岭。

## 第 3 章　财务分析工具栈（下）：企业财务端

### 3.1 三层分工：ERP / 关账 / FP&A

这是最容易搞混的地方，一句话分清：

> **ERP 记录已经发生了什么；关账平台管月度/季度的收口过程；FP&A 预测将要发生什么。**

更准确的表述：ERP 处理交易系统——记录财务、采购、HR、运营发生了什么；FP&A 软件处理规划、预测与建模——预测将会发生什么。**Workday Adaptive Planning 和 Anaplan 是坐在 ERP 交易数据之上的，不是替代 ERP。**

| 层 | 代表产品 | 干什么 | 关键差异点 |
|---|---|---|---|
| **ERP（交易层）** | SAP S/4HANA、Oracle NetSuite、Microsoft Dynamics 365、Workday | 总账、子账、采购、HR | NetSuite 通过 SuiteApps 与 ADP/Gusto/Paychex 集成 |
| **关账（收口层）** | **BlackLine**、Trintech、HighRadius | 对账、分录管理、关账流程 | BlackLine **SAP 集成最深**：原生 S/4HANA 连接器，**实时拉试算平衡表、无需中间件**；Trintech 胜在**工作流可配置性** |
| **FP&A（规划层）** | **Anaplan**、Workday Adaptive | 预算、预测、建模、情景 | Anaplan **企业集成故事最深**：预置连接 SAP/Oracle/Workday/Salesforce，开放 API |

### 3.2 选型的一条经验法则

- **深度 SAP 用户** → BlackLine（原生连接器省掉整个中间件层）
- **流程特殊、需要高度定制** → Trintech（工作流可配置）
- **规划复杂、多维度、跨部门** → Anaplan
- **中小体量、想要一体化** → NetSuite 自带的模块可能就够

### 3.3 对求职者的含义

企业财务系统你几乎不可能在校期间接触到。**但知道这三层分工，在面试聊"财务数字化"时是硬通货**——大多数候选人会把 ERP、关账、FP&A 混为一谈，能清楚说出"ERP 记录过去、FP&A 预测未来、关账平台管中间的收口"，立刻区分开。

配套的架构知识（连续关账、对账引擎、Controls as Code）在配套架构手册第 3 章，这里不重复。

## 第 4 章　Excel：工程化用法与毕业时机

### 4.1 别急着看不起 Excel

财务与投研的现实是：**Excel 仍然是事实上的通用语言**。真正的问题不是"该不该用 Excel"，而是"什么时候该从 Excel 毕业"。

### 4.2 Excel 的工程化用法（在毕业之前先把它用对）

| 做法 | 说明 |
|---|---|
| **Power Query 做取数与清洗** | 把"手工复制粘贴"变成可重跑的查询步骤，这是 Excel 里最接近 ETL 的东西。也支持给 Excel 里的 Python 导入数据 |
| **Power Pivot + 数据模型** | 多表关系建模，摆脱一张大宽表 |
| **一个单元格一个职责** | 输入区、计算区、输出区物理分开，禁止硬编码常数混在公式里 |
| **命名区域代替 A1 引用** | `税率` 比 `$B$3` 可读得多，也不怕插行 |
| **单独一页放假设** | 所有可变假设集中一处——这是 Excel 版的"语义层" |
| **加一页自检** | 把勾稽关系写成公式：分部之和 = 总额、期初+发生-减少 = 期末，不平就飘红 |

> 最后一条最重要。**做完这一条，你的 Excel 模型就有"测试"了**，而这正是配套架构手册里"把勾稽写成可执行测试"的低配版。

### 4.3 什么时候该毕业

出现下面任意两条，就该迁到 Python：

- [ ] 数据量超过几十万行，打开就卡
- [ ] 同一个分析每月要重做一次
- [ ] 需要多人协作且要追溯"谁改了什么"
- [ ] 需要跨多个文件/多个期间做对比
- [ ] 有人问"这个数怎么来的"而你要点开五层公式才能回答

### 4.4 Python 侧怎么选

| 库 | 用在哪 | 选型建议 |
|---|---|---|
| **pandas** | 通用数据处理 | 生态最全、教程最多，**先学它** |
| **polars** | 大数据量、性能敏感 | 比 pandas **快 5–30 倍**、内存更省、API 更一致；**新项目直接上 polars**，老 pandas 代码只在性能真的成问题时才迁移。pandas 用户**一天就能上手** |
| **openpyxl / xlsxwriter** | 读写 Excel 文件 | 自动化出带格式的报表 |
| **DuckDB** | 本地跑 SQL | 在大数据集上和 polars 一样显著优于 pandas；能直接查 CSV/Parquet |

**实用建议**：先 pandas 打底（教程多、遇到问题好搜），感觉到慢了再上 polars 或 DuckDB。别一开始就纠结选型。

## 第 5 章　AI 厂商能力祛魅：各家的 agent 到底是什么

### 5.1 先看 Gartner 的警告

Gartner 2026 年的 **Agentic Analytics 市场指南**明确定义了这个品类：「在数据到洞察的工作流中应用 AI agent，半自主或自主地编排任务」，同时警告存在**广泛的 "agent washing"**——厂商营销宣称与 agent 实际能力之间的落差。

### 5.2 各家的 "agent" 拆开看

**核心事实：这些没有一个是自主的分析调查，它们都只是把分析工作流里某个特定步骤自动化了。**

| 厂商 | 它叫的 "agent" | 实际做什么 | 你该怎么理解 |
|---|---|---|---|
| **ChatGPT** | Agent / Code Interpreter | 在沙箱里**写代码并执行** | 一个会写 Python 的实习生，数据你得传给它 |
| **Claude** | Claude / Code | 同上，长文档理解更强 | 适合"给一堆材料让它读完再算" |
| **Databricks** | Genie | 用复合 AI 系统把**自然语言翻译成 SQL** | 一个 NL→SQL 翻译器，不是分析师 |
| **Snowflake** | Cortex Agents | 把问题**路由到正确的工具** | 一个调度员 |
| **Hex** | Magic | 从自然语言**生成 SQL 和 Python** | 代码补全的加强版 |

**真正的 agentic 分析**的定义是：部署 AI agent 自主调查企业数据——检测异常、分解贡献因素、无需人类指导地交付完整解释。**目前主流产品都没到这一步。**

### 5.3 那该怎么选

一条很实用的规则：

- **临时分析个文件、不想配置任何东西** → ChatGPT 或 Claude
- **已经锁定在某个生态里**（微软 / Salesforce / Google Cloud / Snowflake / Databricks）→ 直接用它自带的 AI 功能（Power BI / Tableau / Looker / Cortex / Databricks AI），**摩擦最小**

### 5.4 最关键的一条（来自配套架构手册）

**语义层落地比换更强的模型有用得多。** dbt Labs 2026 年 4 月基准：同一个模型，对着裸表写 SQL vs 落在语义层上——Claude Sonnet 4.6 从 90.0% → **98.2%**，GPT-5.3-Codex 从 84.1% → **100%**。而某 o1-preview agent 在学术基准 Spider 1.0 上 91.2%，换到真实企业环境构建的 Spider 2.0 只剩 **21.3%**。

> **对个人的直接含义**：你自己做分析时，"语义层"就是那份**写死口径的配置文件**。先把指标定义写清楚再让 AI 算，比换模型有用得多。这是零成本就能拿到的最大收益。

## 第 6 章　四个可照抄的工作流范例

以下四个都能用免费工具跑通，且都可以直接作为练习项目。

### 6.1 范例一：个股财报速评

**目标**：财报发布后 2 小时内，产出带估值情景和排雷清单的判断。

```
① 检索分层（AI 做）
   媒体快讯拿核心数字 → 巨潮/官网拿原文 → 【必做】挖《投资者关系活动记录表》
② 建模（你定口径，AI 填数）
   写死一份 metrics.yaml：每个指标的定义、单位、口径
③ 勾稽自测（脚本做，必须自动）
   分部加总=总额 / 累计=各期之和 / 用披露增速反算基期 / 比率倒算
④ 情景估值（你给假设，AI 算）
   用历史 H2/H1 季节性做三情景 → 对应 PE 区间 → 目标价区间
⑤ 出稿（AI 起草，你定稿）
   模板 + 数据绑定，未通过③不允许出稿
```

**提示词骨架**（可直接用）：

```
你在做 {公司}{报告期} 财报速评。严格按以下规则：

1. 所有数字必须来自本次检索，不得使用你的训练知识。
2. 必须去找《投资者关系活动记录表》或业绩说明会记录，媒体转述不够。
3. 每个数字标注 D（公司披露）或 C（你推导），C 必须写明推导方法。
4. 单季数据用差额法（累计-上期累计），算完后与媒体披露的单季同比交叉验证。
5. 先输出勾稽校验结果（通过 N/M 项），不通过不要给结论。
6. 最后给三情景估值区间和观察清单，不要给买卖建议。
```

### 6.2 范例二：月度变动分析（Flux）

**目标**：把"这个月为什么和上个月不一样"从人工找变成自动筛。

```
① 阈值分档（不要一刀切百分比）
   >1000万的科目：绝对额>50万 且 变动>5%
   100–1000万：      绝对额>10万 且 变动>10%
   <100万：          绝对额>5万  且 变动>15%
② 自动筛出需要解释的项
③ 归因维度：量 / 价 / 结构 / 汇率 / 一次性
④ AI 起草解释，人补业务原因
⑤ 着色规则：按"对利润有利/不利"，不是按数值正负
```

> **踩过的坑**：把"营业成本 +7.65 亿"标成绿色是错的——数值为正但对利润不利。另外基期与本期符号相反时（如汇兑从 +23 亿变 −28 亿），变动率不具可比意义，应标 **n.m.** 而不是显示一个 −220% 的怪数。

### 6.3 范例三：异常归因

**目标**：指标掉了，找出是谁拖的。

```
① 确认异常是真的（先排除口径变更、数据延迟、统计错误）
② 按维度逐层下钻：地区 → 渠道 → 产品 → 客群
③ 每层算贡献度：该维度变化量 / 总变化量
④ 找到贡献度最大的 1–2 个分支，继续下钻
⑤ 停止条件：贡献度分散（说明是系统性因素）或已到最细粒度
```

AI 在这里的价值是**快速生成下钻 SQL 并画图**，但**判断"这个异常值不值得追"必须是你**。

### 6.4 范例四：自动出报告

**目标**：同一份分析每月重跑，格式一致。

```
① 内容与呈现分离
   content.py 存所有结论与数据（单一事实源）
   renderer 分别渲染 HTML / PDF / Markdown
② 图表用脚本生成，不手工画
③ 发布前跑交付自测：
   - 关键数字在各版本间双向一致
   - 无空白页、无缺字
   - 免责声明存在
   - 诱导性措辞扫描 = 0 命中
```

> 这套我实测过：同一份 `content.py` 出 HTML 和 PDF，自测脚本比对两版里 40+ 个关键数字是否一致。**这个"双向一致性检查"能抓到手工绝对发现不了的错。**

## 第 7 章　验证与防错：让 AI 不敢编数字

### 7.1 为什么必须防——一个应该吓到你的数字

**GPT-4-Turbo 配合检索，在一组精心构建的 SEC 文件问答上，81% 的问题回答错误或拒答**；多个模型都存在**系统性编造财务指标**的记录。

这不是黑 AI，是说明：**在财务场景，"看起来合理的数字"和"正确的数字"之间的距离，比你以为的大得多。** 而财务数字的特点是——错了不会报错，它只是静静地错着，直到被审计师或市场发现。

好消息是：**RAG + guardrails + 评估 + 人在环（HITL）的组合，能把幻觉降低 40–96%**，具体取决于技术栈和场景。

### 7.2 五道闸门（按成本从低到高）

**闸门 1：让它引用，不让它回忆**
禁止"根据我的知识"。所有数字必须来自本次检索的具体来源，并附 URL 或文件名。

**闸门 2：确定性重算**
凡是能用公式验证的，一律重算一遍。
> 金融场景的护栏可以校验数值输出是否落在已知区间，或与源数据对账——比如把声称的盈利与官方公布的盈利比对，不一致就标记。

**闸门 3：勾稽断言（财务专属的强力武器）**
财务数据有大量恒等式，普通数据管道没有这个福利：
- 资产 = 负债 + 权益
- 期初 + 本期发生 − 本期减少 = 期末
- 分部之和 = 总额
- 累计 = 各期之和
- 毛利率 = 毛利 / 收入

**把这些写成断言，跑不过就中断。** 这一条能抓住绝大多数编造。

**闸门 4：交叉验证**
用多个模型或多个提示并行比对——**几个模型编出同一个假答案的概率很低**。低配版：让同一个模型用两种不同方法算同一个数（如差额法 vs 反算法），结果必须一致。

**闸门 5：人在环**
在金融这类关键领域，**最终方案必须经过人工验证**。定死哪些环节不可自动通过（见第 8 章边界表）。

### 7.3 自测脚本模板

```python
# 财务分析自测：跑不过就不出结论
import sys

PASS, FAIL = [], []

def ck(name, actual, expect, tol):
    ok = abs(actual - expect) <= tol
    (PASS if ok else FAIL).append(name)
    print(f"{'PASS' if ok else 'FAIL':4s} | {name:40s} | {actual:>12.2f} vs {expect:>12.2f}")

# ① 加总类：分部之和 = 总额
ck("分部收入合计 = 营业总收入", sum(SEGMENTS.values()), TOTAL_REVENUE, 0.02)

# ② 拆分类：H1 = Q1 + Q2
ck("半年度 = 一季度 + 二季度", Q1 + Q2, H1, 0.02)

# ③ 反算类：用披露增速反推基期
ck("上年同期反算", H1 / (1 + YOY_DISCLOSED), H1_PRIOR, H1_PRIOR * 0.001)

# ④ 比率类：倒算并与披露值比对
ck("毛利率倒算", GROSS_PROFIT / REVENUE * 100, GM_DISCLOSED, 0.02)

# ⑤ 交叉类：自算单季同比 vs 第三方披露
ck("Q2 同比交叉验证", (Q2/Q2_PRIOR - 1)*100, Q2_YOY_DISCLOSED, 0.15)

print(f"\n通过 {len(PASS)} / {len(PASS)+len(FAIL)} 项")
if FAIL:
    print("失败：", FAIL)
    sys.exit(1)   # 不通过则中断，不允许出稿
```

> **这段模板是这份文档里最该抄走的东西。** 它不到 30 行，但把"AI 有没有编数字"从一个感觉问题变成了一个可判定问题。

### 7.4 留痕

**存储所有中间步骤**（检索结果、提示词、模型输出），这样出了问题能做事后错因分析。最小实现：每次分析存一个 `manifest.json`，记录 as_of 时刻、数据来源 URL、模型版本、提示词哈希。

## 第 8 章　能力边界与职业影响

### 8.1 哪些工作正在被自动化

**AI 正在自动化传统分析师任务的 30–40%，主要是机械部分**：写 SQL、清洗数据、标准报表。更具体的：写基础 SQL 查询、清洗与格式化数据集、生成标准可视化、写报告摘要、回答遵循常见模式的临时数据问题。

财务侧：生成式 AI 足以自动化大量重复性研究工作、数据清洗和分析初稿。**最容易被自动化的是**：基础记账、入门级股票研究（数据提取）、常规报税。

### 8.2 哪些还在涨价

| 能力 | 为什么 AI 替不掉 |
|---|---|
| **判断力** | 决定"这个异常值不值得追""该给多少倍 PE"——没有标准答案 |
| **沟通** | 把结论讲给不懂技术的人听，并对结论负责 |
| **战略思维** | 知道该问什么问题，而不只是回答被问的问题 |
| **指挥 AI 的能力** | **2026 年数据分析师技能清单里的新增项**：提出精确的问题、验证输出、整合结果 |

2026 年数据分析师的技能分四组：**技术基础**（SQL、电子表格、可视化）、**分析思维**、**沟通**、**指挥 AI 原生工具的能力**。财务分析师侧则是：高级建模 + SQL + BI 工具为必备，且自动化提高了对**扎实判断力**的需求。

### 8.3 一句话结论

> **分析师不是被 AI 取代的，是被「会用 AI 的分析师」取代的。**
> AI 自动化的是任务——数据搜集、初稿建模、总结；分析师依然不可或缺的是**判断、语境、问责与客户信任**。

### 8.4 人机边界表（可直接贴在工位）

| 环节 | 可交给 AI | 必须人做 | 理由 |
|---|---|---|---|
| 检索原始公告 | ✅ | | 可验证、可回溯 |
| 抽取关键数字 | ✅ | | 有勾稽校验兜底 |
| 写 SQL / 画图 | ✅ | | 结果可当场验证 |
| 跑自测脚本 | ✅ | | 纯确定性计算 |
| 生成初稿 | ✅ | | 人定稿 |
| **定义指标口径** | | ✅ | 改一次影响所有下游 |
| **判断异常是否重要** | | ✅ | 需要业务语境 |
| **批准分录 / 关账** | | ✅ | 四眼原则 |
| **下投资结论** | | ✅ | 受托责任不可委托 |
| **对外披露定稿** | | ✅ | 法律责任主体必须是人 |

## 第 9 章　把它变成你自己的技能：90 天路径

前八章是"知道"，这一章是"会做"。**目标：90 天后你能独立完成一个端到端的自动化财务分析项目，并且能在面试里讲清楚。**

### 9.1 技能树（按优先级排死，不要跳）

```
P0 地基（必须，没有它后面全是空中楼阁）
├── SQL：能写多表 join、窗口函数、CTE          ← 面试必考
├── Python：pandas 基本操作、读写文件           ← 一切自动化的载体
└── 财务三表逻辑：知道每个数从哪来、勾稽关系是什么   ← 你的差异化

P1 工程化（把"能跑"变成"可复用"）
├── 把口径写成 YAML，不在代码里硬编码
├── 把勾稽写成断言脚本（第 7.3 节模板）
├── Git：能追溯"这个结论当时用的什么数据"
└── 内容与呈现分离：一份数据出多种格式

P2 AI 协作（放大器，不是替代品）
├── 提示词工程：约束来源、要求标注 D/C、强制先自测
├── 验证机制：五道闸门（第 7.2 节）
└── 知道各家 agent 的真实能力边界（第 5 章）

P3 加分项（有余力再碰）
├── dbt：分析工程的硬通货
├── polars / DuckDB：数据量大了再说
└── 一个 BI 工具：Power BI 或 Tableau 选一
```

### 9.2 三个阶段

#### 第 1–30 天：跑通一次完整流程（手工也行）

选一家你感兴趣的 A 股公司，用**纯免费工具**完成一次财报分析：

- [ ] 从巨潮资讯下载最新财报原文
- [ ] **找到并读完《投资者关系活动记录表》**（这一步是分水岭）
- [ ] 手工整理核心数据到一个表里，标注 D / C
- [ ] 手工验算 5 个勾稽关系（分部加总、H1=Q1+Q2、反算基期、比率倒算、交叉验证）
- [ ] 写出三情景估值区间

**这一阶段的目的不是自动化，是先知道正确答案长什么样**——否则你无法判断 AI 给的对不对。

#### 第 31–60 天：把它自动化

同一家公司，换一个报告期，用代码重做一遍：

- [ ] `metrics.yaml`：把所有指标定义抽出来
- [ ] `fetch.py`：抓取并归档原始件（内容哈希 + 时间戳，只追加不覆盖）
- [ ] `verify.py`：第 7.3 节的自测脚本，至少 10 项
- [ ] `report.py`：内容与呈现分离，输出 Markdown
- [ ] Git 提交每一步，commit message 写清楚改了什么

**验收标准**：换一个季度的数据，脚本能直接重跑出新报告，且自测全通过。

#### 第 61–90 天：接入 AI 并做防错

- [ ] 用第 6.1 节的提示词骨架，让 AI 做检索与抽数
- [ ] **故意不告诉它某个数字，看它会不会编**——这一步你会学到最多
- [ ] 把自测脚本接到 AI 输出后面，不通过就打回
- [ ] 加交叉验证：同一个数用两种方法算，比对
- [ ] 扩展到 3–5 家公司，做横向对比

**验收标准**：AI 编的数字能被你的脚本自动抓出来。

### 9.3 三个可做的练习项目（由易到难）

| 项目 | 难度 | 产出 | 面试价值 |
|---|---|---|---|
| **单公司财报速评自动化** | ★★☆ | 一个能重跑的脚本 + 一份报告 | 讲得清"我怎么防止 AI 编数字" |
| **多公司横向打分卡** | ★★★ | 统一口径的对比表 + 可视化 | 讲得清"口径统一为什么难" |
| **月度自动跟踪** | ★★★★ | 定时任务 + 变化告警 | 讲得清"数据管道的可观测性" |

**第一个项目的完整骨架**（可以直接开始）：

```
project/
├── config/
│   └── metrics.yaml          # 指标定义（你的"语义层"）
├── raw/                      # 原始件，只追加不覆盖
│   └── 20260801_公司_半年报.pdf
├── src/
│   ├── fetch.py              # 采集 + 归档
│   ├── extract.py            # 抽数（可调 AI）
│   ├── verify.py             # 勾稽自测 ← 核心
│   └── report.py             # 出稿
├── output/
│   └── 20260801_分析报告.md
├── manifest.json             # as_of / 来源 / 版本
└── README.md                 # 怎么跑、口径说明、免责
```

### 9.4 面试怎么讲

这套东西的面试价值不在"我会用 XX 工具"，而在**你展示了工程素养**。三个可以直接讲的点：

1. **"我把财务勾稽写成了自动化断言。"**
   → 这句话同时证明你懂财务、懂测试、懂为什么需要测试。大多数候选人只会说"我用 Python 做了数据分析"。

2. **"我知道 AI 会在哪里编数字，并且我有机制抓它。"**
   → 直接对上 2026 年最稀缺的那项能力："指挥 AI 原生工具——提出精确问题、验证输出、整合结果"。

3. **"披露值和测算值我在 schema 层面就分开了。"**
   → 这是一个非常"专业"的细节，说明你思考过数据可信度的分层，而不只是把数拉下来算。

### 9.5 别做的三件事

- ❌ **收集工具**：Wind、Bloomberg 你拿不到，也不需要。**用免费数据把方法跑通，价值一样**。
- ❌ **先学 dbt 再学 SQL**：顺序反了。dbt 是 SQL 的工程化封装，SQL 不熟学 dbt 是空的。
- ❌ **追求一次做完美**：先跑通一个丑陋但完整的流程，再优化。卡在"完美的目录结构"上是最常见的死法——这一点在架构手册第 6.2 节讲 Data Mesh 失败教训时也提到了：组织在"分析瘫痪"上耗掉一年，试图定义完美的、不可变的边界。
