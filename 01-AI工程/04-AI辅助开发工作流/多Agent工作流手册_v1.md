### Orca 的五顶帽子（它到底扮演什么角色）

Orca 不和上面三个 agent 并列——它是**装着它们的那个东西**。五个角色按重要性排：

1. **任务总线**：所有活从这里派发、在隔离 worktree 里执行、在这里回收。
   意义：你的"任务列表"从脑子/备忘录移到了一个有状态追踪的系统里。
2. **并行执行引擎**：六种拓扑（见第五节）的宿主。同题对比只是其中一种。
3. **审查工作台**：内嵌 diff 注释器——agent 产出的每一行改动在这里过目、
   写反馈、打回重做。**人在环的质量闸门设在这里，不在终端里。**
4. **注意力管理器**：通知 + 未读标记 + 手机同伴 App（E2EE 已配）。
   agent 跑 20 分钟的死等时间被释放：你去干别的，跑完它叫你；
   在外面时手机上审批。多 agent 体系的真正瓶颈是你的注意力，不是算力。
5. **观测面板**：订阅用量 + 任务历史（orchestration.db）。
   配合 `omp usage` 构成完整的资源视图。

另有三件低频但关键的武器：**Design Mode**（点选网页元素直接进提示词，调前端用）、
**Computer Use**（agent 操作桌面应用，谨慎开）、**Quick Open**（跨 worktree/文件/agent 全局跳转）。

**一条总原则**：接到任务先花 10 秒问"这活谁干"——想不清楚就查下面的路由表。用错车道不是浪费钱，就是浪费你最稀缺的 Claude Pro 额度。

## 四、一天的标准节奏（habit anchor）

**开机三件事**（1 分钟）：
1. 开 Orca（驾驶舱起来，用量看板在眼前）
2. `omp usage` 扫一眼——Antigravity 池昨天用了多少？**长期低于 30% 说明你又回到"什么都塞给 Claude Code"的老习惯了**
3. 看 Orca 通知：昨晚挂的后台任务有没有跑完

**任务进来时**：10 秒路由（查上表）→ 该开 worktree 的开 worktree → 干活。

**收工前**（可选但强烈建议）：把明天要跑的批量活/长任务挂给 opencode 或 Orca 后台，睡觉时间也是 $12/5h 窗口的时间。

## 五、并行阵型手册（拓扑 · 场景 · 实操）

阵型不要按领域记（那会记到十几个），按**拓扑**记——只有六种，任何场景都是这六种的实例。

### 5.1 六种基本拓扑

| 拓扑 | 一句话 | 解决什么 | 收口方式 |
|---|---|---|---|
| **① 分工并行**<br>fan-out 异题 | N 个 agent 干 N 件**不同**的事 | 吞吐（最常用） | 全都要，各自合并 |
| **② 同题多方案**<br>fan-out 同题 | N 个 agent 干**同一件**事 | 择优（方案不确定） | 只要一个，其余丢弃 |
| **③ 流水线**<br>chain | 拆解 → 并行执行 → 汇总 | 批量机械活 | 汇总成一份 |
| **④ 审查 / 对抗**<br>two-stage | 一方产出，另一方挑刺 | 质量 | 产出 + 修订意见 |
| **⑤ 网格扫描**<br>grid | 同一流程跑 N 组参数 | 探索最优解 | 一张对比表 |
| **⑥ 影子对照**<br>A/B | 新旧两套方法跑同一批输入 | 验证（重构/换模型） | 差异报告 |

**④ 的两个变体值得区分**：
- **审查**（不对称）：A 写、B 审，B 是权威 —— 用于代码质量
- **对抗**（对称）：A 正方、B 反方互相攻击，**你当裁判** —— 用于技术选型、量化策略多空论证、"这个项目该不该做"

**⑥ 是最容易被忽略但最省事的**：你刚给 QRP 加了横截面 IC 层，正确的验证方式就是让新旧两套 IC 同时跑同一批因子，看结论差在哪——而不是只看新代码测试过没过。

### 5.2 场景 → 拓扑映射（用的时候查这张表）

| 场景 | 拓扑 | 按什么切分 |
|---|---|---|
| 多仓库/多任务同时推进 | ① | 按任务 |
| 多源调研（GitHub/中文社区/英文社区/视频） | ① | 按信息源 |
| 求职季批量投递（N 个 JD 各一套材料） | ① | 按岗位 |
| 文献批量精读 | ① | 按论文 |
| 知识库整理/月度审计 | ① | 按目录 |
| 技术选型、架构方案不确定 | ② | 同题分发三家模型 |
| 面试模拟（技术面/行为面/case 面同时压） | ② | 同题不同角色 |
| 批量重构、系列文档生成 | ③ | Sisyphus 自动拆 |
| 代码质量把关 | ④审查 | omp 写 → Claude Code 审 |
| 要不要用某方案 / 策略多空辩论 | ④对抗 | 正反两方 |
| 因子族、参数网格回测 | ⑤ | 按参数组合 |
| 重构验证、换模型验证 | ⑥ | 新旧两版跑同一输入 |

### 5.3 实操教学：跑一次并行的五个步骤

并行的成败**九成在任务设计，一成在点按钮**。所以这里重点讲设计。

**第 0 步：先判断该不该并行**（见 5.5 的反例）

**第 1 步：切分 —— 保证块与块之间零依赖**
坏切分：「A 改数据层、B 改依赖数据层的业务层」→ B 必然等 A，并行退化成串行还多了冲突。
好切分：「A 修 kairos、B 修 pdf-pilot、C 更新文档」→ 三个仓库互不相干。
自检一句话：**如果 A 失败了，B 还能不能照常完成？** 不能，就不是并行。

**第 2 步：写提示 —— 每个 agent 必须自带完整上下文**
并行的 agent 之间**互相看不见**，也看不见你脑子里的背景。模板：

```
【任务】<一句话，动词开头>
【上下文】<仓库/文件路径、相关背景、已知约束>
【产出物】<具体到文件：改哪个文件 / 生成什么文件>
【验收标准】<可机验的条件：测试通过 / 有 N 条要点 / 格式符合 X>
【禁止】<不要碰的东西，如"不要改 README"、"不要动其他目录">
```

「禁止」那行别省——并行时最常见的事故是两个 agent 同时改了同一个公共文件。

**第 3 步：分发与隔离**
- 在 Orca 里：每个任务建一个 worktree，选 agent（可以给不同任务派不同 agent），提交
- 同题多方案（拓扑②）：同一份提示分发给不同厂的 agent（Claude Code / omp / opencode），**必须不同厂**——同厂模型盲区共振，对比不出信息
- 派活原则回查第三节路由表：难的给 Claude Code、量大的给 omp、机械的给 opencode

> **⚠️ worktree 的视野盲区（2026-07-25 首次演练实测踩到）**
> worktree 是从 git **检出**的，所以 `.gitignore` 排除的文件在里面**根本不存在**
> （连带只含被忽略文件的子目录也不存在）。
> 演练中 Agent C 因此报告「16 份 PDF 一份都不在磁盘上」——它的观察在自己
> 环境里 100% 准确，但据此推断整台机器上没有，就错了。
>
> **规避**：任务涉及被 gitignore 的文件时，在提示词里写明
> 「X 类文件在主仓库存在但你的工作副本里看不到，不要据此判断它们不存在」；
> 或者干脆不用 worktree，让该 agent 直接在主仓库跑。

**第 4 步：跑起来后你去干别的**
这是并行的**真正收益点**。别盯着看——开通知、标未读，agent 完成时它叫你。
你在这段时间该做的：干主线任务（阵型①的一路本来就是你自己），或者休息。

**第 5 步：收口**（见 5.4）

### 5.4 收口与冲突处理

| 拓扑 | 怎么收 |
|---|---|
| ① 分工并行 | 逐个审 diff → 逐个合并。**互不相干所以基本不冲突**（实测：3 agent 改 9 个目录，零冲突）。注意 agent 可能只改文件不 commit，收口时先替它们提交 |
| ② 同题多方案 | 三份并排读 → 选一份合并，其余 worktree 直接删。**三份分歧的地方 = 这题真正的难点**，值得单独想清楚 |
| ③ 流水线 | Sisyphus 已汇总，你审最终产出 |
| ④ 审查/对抗 | 审查意见回灌给原 agent 改；对抗的裁决由你做，把结论写进决策记录 |
| ⑤ 网格扫描 | 汇总成一张表再看，**不要逐个看**（会陷入细节丢失全局） |
| ⑥ 影子对照 | 只看差异清单：差异为零 = 重构安全；有差异 = 逐条判断是修复还是回归 |

**冲突处理**：真冲突了（两个 worktree 改了同一文件），不要手工 merge——把两份 diff 一起丢给 Claude Code，让它理解意图后重写一份。语义合并比逐行合并可靠。

**非代码场景的差异**：笔记/文档的 Markdown diff 比代码 diff 好审得多，收口更快；但要注意**产出目录别重叠**（每个 agent 写自己那一块，最后你合并索引）。

### 5.5 不要并行的三种情况

1. **任务本身要探索**：你还不知道要干什么，并行只会得到三份跑偏的东西。先单线程想清楚再拆。
2. **块与块有依赖**：见第 1 步自检。
3. **收口成本 > 并行收益**：三个 agent 跑 5 分钟，你审 40 分钟——不如自己串行做。**小任务不要并行。**

## 七、持续提效的复利机制（体系不退化的关键）

工具装好只是零点。提效来自三层循环，每层都有明确的触发器：

**第一层：观测（发现瓶颈）**
- 每周五 4 锚点检查（第九节）+ `omp usage --history -d 7` + Orca 用量面板
- 问一个问题：**这周哪类任务我干得最慢/最烦？** 那就是下周的优化对象

**第二层：沉淀（一次劳动多次收益）**
- 同类提示写第 3 遍 → 固化成 Claude Code 技能或 omp 扩展（你已有 33 个技能，证明这条路你走得通）
- 打得好的会话 → `omp --export` 成 HTML 进知识库，成为下次同类任务的起点
- 每次被某个 agent 坑了 → 在手册"别这么干"清单里加一条

**第三层：自动化（把人从循环里拿掉）**
- 重复出现的定时活（周报、数据更新、知识库整理）→ 挂 cron/scheduled task
- 长任务一律后台 + 通知，人只出现在决策点和审查点
- 移动端审批：等车/排队时间处理 Orca 未读

**退化警报**：如果连续两周三层循环一层都没触发，体系正在退化成"只是多装了几个终端"——回到第一层重启。

### 外部范式引入记录（2026-08-01 · YC QM）

> 来源：`06_行业观察/04_案例研究/20260801_YC开源QM多Agent办公系统_学习笔记.md`
> QM 是 YC 用于运营自身公司的组织级 multi-agent harness。以下是**逐条评估后**的取舍，
> **不是照单全收**——记录否决理由与记录采纳同等重要。

#### ✅ 采纳一：最小审计（第四层）

**问题**：Orca 的 `orchestration.db` 记录的是"任务跑了"，不是"**哪个 agent、用哪个模型、碰了哪些文件**"。

**为什么现在必须补**：资产总览里已写死一条硬约束——「简历/项目代码/面试话术一律不走免费模型」。
但目前**没有任何机制能事后验证这条规则有没有被违反**。若某份敏感文件被送进 `nemotron-3-ultra-free`
（NVIDIA 官方明写会记录会话），事后无法追溯。**约束没有审计 = 约束不存在。**

**个人版做法**（不需要 QM 那套组织级审计）：

- agent 产出的提交，commit message 末尾带标识：`[agent: kimi/zen-big-pickle]`
- 涉及敏感目录（`04_项目与作品集/`、`05_求职面试/`）的任务，**只允许付费模型**，并在提交里注明
- 每周五 4 锚点检查时，`git log --grep="\[agent:" --oneline -20` 扫一眼这周谁干了什么

#### ✅ 采纳二：按项目隔离配置（做法采纳，理由改写）

**QM 的原论证**（每 scope 独立 memory 防污染）**对个人用户不成立**——项目数量少，
跨项目记忆污染的实际发生率极低，为它上一套 sandbox 是过度工程。

**但换一个理由就成立**：按目录隔离配置 = 天然实现"这个目录只准用付费模型"。

```powershell
# 敏感项目用独立数据目录 + 独立 config（只配付费模型）
KIMI_CODE_HOME="$PWD/.kimi-secure" kimi
```

官方文档「Isolated test environment」一节即此用法。**采纳的是做法，不是原论证。**

#### ❌ 评估后不采纳：webhook + monitor 触发器

| 项 | 否决理由 |
|---|---|
| **webhook** | 需要稳定公网入口。个人电脑没有，这是 QM 作为云端部署的组织级需求。QM 笔记第四节自己也把 Slack/云依赖列为不该照搬 |
| **monitor**（变化才触发） | 本节第三层的 cron/scheduled task 已覆盖现有场景（周报、行业跟踪、知识库整理）。monitor 的价值在"高频数据源 + 低频变化"，当前无此场景 |

**结论：加了是纯增复杂度、不产生收益。**
记录在此是为了防止三个月后（被人或被 AI）重复提出同一建议时，还要再论证一遍。

## 八、每周学习操作系统（确保周周有新产出、新收获）

学习不靠意志力，靠**节拍 + 容器 + 队列**。三样都给你定制好了：

### 节拍（写进日历锁死，全周 ≤ 4 小时）

| 时间 | 时长 | 动作 |
|---|---|---|
| 周一早 | 15 min | **定题**：从主题队列取本周主题，写一句话"本周产出物是什么"（一句话写不出来 = 主题太虚，换） |
| 周二~四 | 每天 ≤30 min | **并行跑起来**（拓扑①）：agent A 精读出笔记、agent B 跑最小复现，都挂后台；你只读 A 的笔记、审 B 的 diff |
| 周六 | 2 h | **产出日**：复现收尾 → 进容器（见下）；有余力就顺手清一个自家仓库待办 |
| 周五晚 | 10 min | **复盘**：勾 4 锚点 + 记"本周最烦的任务" + **收集箱清零**（没被用到的收藏直接进 99_归档，不留恋） |

### 容器（产出往哪放，三选一即算完成）

1. **paper-to-practice 仓库**——复现代码和 takeaway 的天然容器（这是你自己建的仓库，别让它停更）
2. **knowledge-notes 仓库**——你 14 星的最有流量资产，笔记公开化有复利：一份笔记 = 学习产出 + GitHub 活跃度 + 面试谈资
3. **实习积累知识集合**——对内沉淀，配合 00_INDEX 月更

### 主题队列（8 周一轮，对准你知识库自标的缺口）

| 周 | 主题 | 对准什么 |
|---|---|---|
| 1 | 系统设计基础（缓存/队列/一致性） | 08 目录 P0 缺口 |
| 2 | 测试与工程规范（TDD/CI 深化） | 09 目录 P0 缺口——今天 7 个 PR 的方法论系统化 |
| 3 | Agent 工程深水区（tool use/记忆/编排） | 主战场 02_AI工程 |
| 4 | RAG 与向量检索实战 | 02 目录既有积累的深化 |
| 5 | 量化 ML（因子 ML/组合优化） | 差异化资产，接 QRP/kairos |
| 6 | LLM 评测与可观测性 | 面试高频，且你有 freeswap 素材 |
| 7 | 容器化与部署（Docker/CI 到上线） | 08 目录缺口下半场 |
| 8 | **机动位：当周最热的新东西** | AI 时代快速适应的专用槽位 |

跑完一轮回到 1 加深。机动位是刻意设计的：**每 8 周强制接触一次最新事物，适应速度就有了制度保障**，不靠焦虑驱动。

### AI 时代适应的两个月度动作

- **每月一次工具链审计**（30 min）：`omp usage --history` 看虚耗、淘汰一个月没用的工具/技能——2026-07-12 那次审计干掉了死代理和 9 个沉寂工具，证明这个动作值钱
- **每月一次定向调研**（用 `/agent-reach`，30 min 封顶）：只调研"我下个月要用的东西"，不做无目的刷讯

### 效率的本质（为什么这套会比"多看多学"快）

传统学习：你读 → 你懂 → （大概率停在这）。
这套系统：**agent 读第一遍，你只处理蒸馏后的笔记和能跑的代码**——你的时间全部花在最高价值的两个环节（判断与整合），机械环节（检索、初读、抄代码、格式化）全部外包给三个免费/廉价车道。每周 4 小时投入，产出一份可公开的复现 + 一份进库笔记，这个比率靠人肉是做不到的。

## 九、这套体系怎么服务"转码"这件事

工具不是目的。这套体系对你 finance→AI 应用工程转型的价值在三个地方：

**1. 它本身就是面试素材。**
"我用三份订阅搭了一个三车道多 agent 体系：按任务复杂度和配额经济性路由，用 Orca 做 worktree 隔离的并行对比，Sisyphus 做批量编排"——这段话是任何 AI 应用工程面试里都站得住的系统设计叙事，而且每个细节你都能答上追问（因为是真的）。

**2. 它把 portfolio 迭代成本打下来了。**
2026-07-06 一天之内 7 个 PR（前视修复、断路器接线、横截面层）全部 TDD + CI 合并——这个吞吐就是多车道的直接产出。你的仓库还有现成的待办可以按同样节奏清：
- kairos：journal 落盘（20 分钟）
- pdf-pilot：MinerU 适配 mineru 2.x + 公式检测改字体启发式（各半天）
每清一个都是一次"发现问题→修复→测试→合并"的完整叙事。

**3. 它是 forcing function，不是又一份计划。**
你的模式是强收集弱执行——所以这份手册刻意不设"学习路线"，只设四个可检查的行为锚点，开发/学习/求职各有覆盖：
- [ ] 本周 omp 会话数 > 5（快手车道真的在用）
- [ ] 本周至少 1 次多 agent 并行（六种拓扑任一，证明不是单终端时代）
- [ ] 本周至少 1 个 PR 合进自己的仓库（开发在产出）
- [ ] 本周至少 1 条笔记或复现进知识库（学习在产出，第八节学习系统的出口）
每周五花 2 分钟勾一遍。连续两周勾不满，说明体系有问题——回来改手册，而不是自责。
